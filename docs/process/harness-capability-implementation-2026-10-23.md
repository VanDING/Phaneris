**Ownership and compatibility.** Pi remains the only agent loop; the existing Runtime Host/Kernel retain input, execution, T1/T2, usage and recovery authority. Canonical session-tool definitions remain the single schema source. Guidance is derived from the existing workflow corpus: resident contracts, exact documentation routing, questions, communication and short resource rules remain available; Pages, deliverables, session management, secondary models and configuration workflows activate with their tool families. The complete previous corpus is still checked against all 48 platform/feature baselines through the diagnostic full-guidance path.

`phanerisResult` is additive host-owned result metadata. Source completeness is distinct from complete tool-return storage; missing historical metadata remains unknown. Read evidence hashes the actual buffer consumed by the SDK, not a later file read. Multiple original ranges can establish delivery only for the same version. Shell commands and derived text do not establish complete original reading. A receipt records delivery, never comprehension or permission.

Media and program values remain intact. Generic text projections save the exact tool return and canonical blocks with hash identities before T2, then expose deterministic head/tail text. File reads keep exact range semantics and original recovery. Storage failure returns a truthful incomplete-delivery status without claiming a saved file or repeating business effects. T2 stores the representation Pi receives; canonical restoration does not stringify that representation into a new textual envelope.

Existing `largeResults` and `midTurnMessages` preferences are preserved on disk for compatibility, but their automatic interception is retired; their settings controls explicitly show this and are disabled. Advice wording is updated in all seven supported locales. Explicit `decide`, `call_llm`, Guarded and usage accounting remain available within their existing permissions.

**Validation.** The expanded `bun run verify:model-harness` produces JSON and source/fixture manifests using the existing verification artifact mechanism. It covers real Pi subprocesses, Host, SQLite, public SDK APIs and controlled loopback inference, plus an actual SessionManager with a held decision endpoint. Fixture inference proves mechanics, not model quality.

The closing `bun run verify:model-harness` passed **84 scenarios**: contract 21, effects 17, prompt assembly 7, capability/evidence 11, real Pi 11, tool order 6, task context 4 and input continuity 7. The real Pi fixture made 12 provider requests, with seven tool calls, a deliberately rejected request, independent utility inference and a resumed main turn. It confirms that tool schemas and Pages guidance reach the actual provider request in the inner loop, and that active tools survive a session rebuild.

Two additional failure cases were reproduced before their fixes: Pi emits `message_start` even for a rejected provider request, and literal original files can contain historical preview markers. Reading is now acknowledged only after a completed non-error assistant response, before its next tool call; typed original coverage takes precedence over legacy text heuristics. Merely preparing or committing a result does not acknowledge delivery. The original 48 platform/feature prompt baselines still pass; their full workflow corpus is a diagnostic comparison, not the default resident prompt.

Public SDK adaptation: Pi 1.3's forced opaque prompt discards request-time sections. Main sessions therefore set the public `before_agent_start.systemPromptOptions.customPrompt` and use `context_with_system` sections for active capability guidance. Utility sessions keep their independent forced prompt and empty tools. There is no SDK private-state patch or second agent loop. The real Pi fixture verifies both directions of isolation and distinct durable utility usage.

Additional acceptance passed: `bun run typecheck:all`, `bun run typecheck:scripts`, `bun run lint`, all four i18n gates, `bun run identity:check`, `bun run version:check`, `bun run check:docs` and `git diff --check`. The existing shared acceptance suite passed 83 tests. Existing durable crash (8), independent Pi (6) and Guarded refinement (6) scenarios also passed. Detailed source identities, reports, commands and scope are archived in the [acceptance evidence](../verification/results/harness-capability-2026-10-24/index.json). Full fixture/database trees remain in their recorded local run directories; the archive contains selected reports, original manifests and gate logs, not those bulky trees.

Environment: Windows x64, Pi SDK 1.3.0, actual Bun 1.4.2. The repository distribution pin is Bun 1.4.3; the static distribution check validates that pin, not the executable used for these local runs. These results do not establish acceptance on the pinned runtime, Linux/macOS or signed installers.

**Boundaries.** No production account, user settings file, connected service, historical conversation or external repository was mutated. No model provider benchmark was run. Context allocation is a conservative estimate, not a tokenizer-independent capacity guarantee; native Pi compaction, handoff and manual policies remain authoritative. Arbitrary shell output has no invented range proof. HTTP pagination with no server snapshot contract remains unknown. Native non-Windows isolation, signed installers and statistically meaningful quality comparisons require their own environment/evidence.

Hash-addressed evidence lives under the existing session `long_responses` directory and is retained with the session, rather than temporary transport snapshots. The implementation adds no automatic deletion or independent evidence GC. A future retention policy must account for referenced history and recovery. Small exact results remain inline in the canonical outcome.

Rollout: this branch is a reviewable implementation candidate. The new deterministic result handling, capability exposure and input policy are active in this branch; they have not been released. Merging, release packaging and promoting defaults after live quality evaluation are separate decisions; no measured quality improvement is claimed. Existing effect barriers and model configuration remain the evidence-gated H5 decision.
