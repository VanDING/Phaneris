前端视觉系统审计

这份文档把先前分开看的两件事合成一条主线:你在截图上看到的问题(面太灰、圆角不一致、顶部不齐、边界不清、卡片过宽、侧栏偏大) 与全项目统计出来的成因(尺度没有 token、六类体系并存、门禁有盲区、无障碍缺陷、债务随新功能增加)。 它们不是十来个孤立毛病,而是同一套"缺失的约束"在八个维度上的投影。

三个根因 + 一条趋势(全文都围绕这四句)

  • 根因 A · 亮色主题没有"面"的层次。面板、卡片、输入框全是 #FFFFFF;画面里唯一的"灰"来自 macOS 材质(实测 #E8E8E9,随壁纸变化)。→ 解释"背景偏灰"与"边界不清"。
  • 根因 B · 没有共享的内容边与栅格。侧栏首行比面板顶边低 7.0、文字中心低 5.5;转录列 20px 内距 vs 输入区 16px;列宽 840。侧栏本身也在这条里(行高由内距推导,不是命名尺寸)。→ 解释"顶部不齐""卡片过宽""侧栏偏大"。
  • 根因 C · 尺度没有 token,只有基数。引擎给"一个 6px / 一个 15px",不给"可选集合";圆角 328 处字面量、10 个取值;字号 590 处、8+ 取值;填充 204 处、12 个 alpha。→ 解释"圆角不一致",也是所有细节问题的上游。
  • 趋势 · 债务在增长,不是遗留。违规最集中的文件里,除 AppShell / TurnCard 外全是我们最近新写的功能(session-decisions、trajectory、kanban)。不做约束,半年后数字会回到今天。

§0

实测基线

后文所有"实测"都来自这一节。方法:在你提供的截图(3424×2382)上逐像素扫描——颜色取样、水平/垂直边界扫描、圆角弧线最小二乘拟合(残差 < 0.35px 才采信); 代码侧用正则统计命中次数(口径见 §10)。

标定:为什么是 @2x

  • 窗口内宽实测 3199 原始像素 ↔ 若为 1600 css 则比例 1.9994;
  • 侧栏实测 512 原始像素 ↔ 恰好 256 css。
  • 两处独立标定互证 → 取 @2x,下文所有长度 = 原始像素 ÷ 2。
  • 反例:交通灯按钮实测 28px(=14pt),说明这台机器的窗口按钮比经典 12pt 大,所以不用它标定(按 12pt 会得到 2.33 的错误比例)。

§1

面(surfaces):一切边界问题都源于这里

这一章解释三件你直接感觉到的事:背景偏灰、卡片边界不清、以及"要不要给侧栏上色"这个决策。 它们其实是同一个问题的三个侧面 —— 我们的界面里,"面"没有层次,而唯一的灰不是我们选的。

1.1 背景为什么偏灰:因为它不是我们的颜色

侧栏 / 标题栏
#E8E8E9(232,232,233)—— 两者同色,合计构成一个 L 形灰区:横 1600×45.5、纵 256×1070
面板
#FFFFFF —— 中间没有任何过渡色
窗口之外
#000000 —— 证明这块灰是"系统材质 + 桌面"的合成结果
上游同位置
navigator #F2F3F4(242)、paper #FCFDFE —— 画布比我们亮 10 个灰阶,纸面不是纯白

代码链:为什么它由系统决定

  • window-manager.ts:248 → vibrancy: 'under-window' + visualEffectState: 'active'
  • index.css:558 → html, body, #root 只有高度与 overflow,没有背景色
  • AppShell.tsx:2636 → 侧栏背景是条件性的:hasThemedNavigatorSurface && "bg-navigator"
  • default.json → 没有设置 navigator(主题注释也写明"未显式作者化时侧栏保持透明")

后果:这个灰随用户壁纸与系统外观变化,我们无法保证任何一台机器上的背景色;而且它恰好比我们想要的暗一档。

着色决策:三个方案与量化后果

先明确"整体感"从哪来:今天标题栏、侧栏、面板间隙、窗口留白全是同一块材质,连成一个连续场 —— 这是"什么都没画"的副产品。 因此风险不是"上色",而是只给一部分上色(侧栏上色、标题栏留材质 → 左上角出现 L 形分裂)。只要两者同源,连续场就保住。

1.2 面板边界:一条偏蓝的 1px 线,零阴影

实测剖面(从画布到面板内部)

画布 232 → 紧贴面板 229 → 边框 227,229,236 → 面板内 255
                 ↑ 阴影峰值 Δ3(肉眼≈0)   ↑ 蓝相 B−R=9   ↑ 白

也就是:高程完全没有落在阴影上,边界完全由那条 1px 线承担;而这条线偏蓝,画布却是中性灰 → 冷暖不一致,边界看着"脏"。

代码:2% 的阴影在数学上存在、视觉上为零

--shadow-minimal: 0 0 0 1px var(--border),
                  0 1px 2px mix(shadow 2%),
                  0 3px 6px  mix(shadow 2%);
--shadow-middle : 1px 环 + 0 4px 12px mix(4%)
--theme-shadow-color: #20232C · shadowStrength: 0.04

2% 的黑在 6px 模糊下峰值不到 1%;--shadow-minimal 被用了 214 处(84% 的表面),所以整个界面是平的。

现状

改法 ① 边框中性化

亮色 --border: #E3E6ED → #E6E6E8(或 color-mix(in oklab, var(--foreground) 10%, transparent)); 暗色 #343946 也偏蓝(B−R=14),同步去蓝。改动最小、收益最直接。

改法 ② 卡片级高程

新增 --shadow-card(中性边 + 5–6% 阴影),只用于卡片/浮层/输入卡;不要全局加重(214 处一起变会过头)。

改法 ③ 间隙也要一起处理

列表↔内容之间 6 css 的间隙里叠出了 4 css 的 #E2E2E5 灰带(缩放条 2px 线 + 两侧阴影),而侧栏↔列表只有 1 css。两个接缝的视觉重量不一致,应让间隙里的东西与面板边框同色同权重。

1.4 两个"面积性"问题:气泡与纯白

用户气泡融进背景

气泡 #F3F3F3 与画布 #E8E8E9 只差 11 个灰阶;而它是固定色 --user-message-bubble: #F3F3F3, 没有相对"它所在的纸面"计算。建议改为按前景混合的填充(气泡在纸面上应该比纸面暗一档,而不是与画布竞争),或至少压到 #F0F0F0 拉开距离。

大面积纯白

亮色下 background / paper / card / popover / input 全部是 #FFFFFF 或近白。 纯白大面积铺开会让旁边的灰显得更脏,也让"哪块是凹陷"无法从颜色判断。建议纸面保留纯白,把输入框与代码块改成下沉色(如 #F7F8FA), 让凹陷一眼可辨 —— 这也顺带解决"输入卡和消息卡长得一样"的问题。

2.1 圆角:三个来源、十五个取值,而且"嵌套"设计是死代码

三个来源

① 硬编码
328 处 / 10 个取值:8px 119 · 6px 73 · 4px 50 · 10px 32 · 3px 13 · 2px 10 · 5px 9 · 12px 6 · 16px 4 · 9px 3
② 尺度类
478 处,值为 --theme-radius × k = 3 / 4.5 / 6 / 9 / 12 / 18 / 24(含非整数);直接引用 var(--radius…) 的地方 0 处
③ 面板专用
--theme-panel-radius(6),它覆盖了 RADIUS_EDGE(14)/RADIUS_INNER(10) → 那两个 fallback 永不生效

为什么眼睛会觉得"不一致"

圆角是同族关系的信号:两个嵌套圆角只有满足 内 = 外 − 间距 时才同心。 我们的窗口是 10–12、面板是 6,而两者之间只隔 1–5px → 差值被直接看见。上游把这条写成了算术(连体内角 = 0、外角 = --radius-lg),不是靠手感。

目标:4 级 + 嵌套公式 
--r-panel: max(6px, calc(var(--r-window) - var(--panel-inset)))
--r-card:  var(--r-panel)     /* 卡片与面板同族 */
--r-row:   6px                /* 行、菜单项 */
--r-chip:  4px                /* 徽标、芯片、小按钮 */

迁移顺序:①先让 RADIUS_EDGE/INNER 生效(或把主题字段拆成 edge/inner 两个);②按映射表 codemod 替换 328 处(8→card、6→row、4→chip、10/12→panel); ③加门禁禁止新字面量(见 §7.3)。

"质感"里最容易被忽略、也最容易被眼睛抓到的是对齐。这一章用三个实测把这件说清:顶部对齐、内容边与列宽、窗口内距与接缝。

§5

状态与反馈:同一件事有多种强度

状态(悬停/选中/按下/禁用)是"界面是否活"的关键。我们的问题是:没有状态 token,于是每个组件自己定一个强度 —— 这既是 §2.4 的 12 个 alpha,也是"同一屏里两个选中态看起来不一样重"的直接原因。

实测:同一语义,两种强度

侧栏选中行
#DBDBDC ≈ 前景 7% 叠在灰底上(看起来明显)
列表选中行
#F8F9F9 ≈ 前景 3% 叠在白底上(几乎看不出)
hover 填充
最常用的写法 bg-foreground/[0.03](53 处)与 /5(246 处)→ 3–5%

3–5% 的填充在部分显示器/亮度下几乎不可见,于是"能点的东西看起来不能点"; 而侧栏用了 7%,又显得过重。两者都不是错,错在没有统一。

目标:只保留三档 + 一个气泡档 
--fill-hover:    3.5%   /* 悬停 */
--fill-selected: 6%     /* 选中 */
--fill-pressed:  8%     /* 按下 */
--fill-bubble:   5.5%   /* 气泡(相对纸面) */

附带一条:触摸设备上"悬停才出现"的功能

我们已经有 data-touch-reveal 机制(index.css:1585:在紧凑模式下把 opacity-0 强制为 1),也已在若干处使用。 但全项目仍有约 32 处"opacity-0 … group-hover:opacity-100"的模式,其中一部分没有加这个属性 —— 在触摸设备上那些操作等于不存在。

做法:把"hover 才出现的操作"列为设计规则:要么默认可见(降权显示),要么必须带 data-touch-reveal; 可以用一条 lint 规则来兜(检测 opacity-0 + group-hover 同现且无该属性)。

状态清单(建议统一后):默认 / 悬停 / 选中 / 按下 / 聚焦 / 禁用 —— 六态各对应一个 token, 组件不再自己发明数值。禁用态目前是 opacity-50 之类的写法,建议换成 --text-disabled + 填充降档。

§6

无障碍:本次审计里最该优先处理的一块

视觉微调影响"好不好看",而无障碍影响"能不能用"。我们在这方面有一个系统性缺陷,而且它不是新问题。

6.1 焦点可见性:我们把原生焦点环全局关掉了

全局规则
index.css:599 *:focus-visible { outline: none; --tw-ring-width: var(--ring-width); … } —— 原生焦点环被全局关闭,改由 Tailwind 的 ring 承担
环的强度
--ring-width: 1px · --ring-offset: 0px;上游是 outline: 2px solid + offset 2px
显式焦点样式
全项目 318 处 focus-visible/craft-focus 写法;但其中 craft-* 角色类只被 35 个文件使用
焦点抑制
192 处 outline-none / focus:outline-none / outline: none

结论:凡是没有显式写 ring 的可点元素,键盘聚焦时没有可见反馈。而角色层覆盖率只有 9%(35/396 文件), 其余 192 个文件直接写 <button> —— 也就是说,这个缺陷的暴露面是"大部分界面"。

为什么这条优先级最高

  • 它影响的是键盘用户能不能操作,而不是"看起来是否精致";
  • 修复成本极低:把全局规则从"关闭"改成"给一个默认环",再把 craft-* 作为自定义样式的例外;
  • 它顺带解决"1px 环太弱":改成 2px + 2px offset 与上游同级即可;
  • 这条改完,后续所有组件的焦点表现自动变好 —— 不需要逐个组件补。

§7

体系与门禁:token 归属、六类并存、规则的盲区

7.1 token 那件事的完整答案:三层问题

"是引擎缺失,还是引擎有而我们没应用?"——两者都有,而且是三层叠加。逐类核对如下。

类别引擎是否提供实际使用缺口
圆角有--theme-radius 一基数 + 派生 7 档;但直接引用 var(--radius…) 0 处 被绕过:328 处字面量。引擎给"基数 × 系数",不给"四级语义"。
字号只有一半仅 --font-size-base 一个值 缺尺度:没有字号角色 → 590 处字面量只能用。
行高 / 间距只有一半density 三档 → 只输出 4 个内距;无 gutter / 卡内距 / 命名行高 缺行高与栅格:行高成为内距副产品 → 407 处任意值间距。
状态填充没有--fill-* 全项目 0 处(不存在) 完全缺失 → 204 处手写、12 个 alpha。
高程两个旋钮只有 color + strength;四档结构硬编码在 CSS;84% 挤在最弱档 缺语义分级(flat / card / floating),也不能整体调强弱。
颜色角色多套并存主力是 shadcn 层 1394 + 前景阶梯 1248;主题语义层 146;--surface-* 0 缺唯一入口:新组件不知道用哪套(详见 7.2)。
动效两套motion.css 与 lib/motion.ts 数值不同;27 处时长字面量 缺唯一来源。
z-index有16 个 token 齐全 + lint 规则(error)规则有形式盲区(见 7.3)。

三段话总结:①引擎缺的是"尺度"(可选集合),不是"值";只给一个基数等于没有约束 —— 6 的 0.5/0.75/1/1.5/2 倍是 3/4.5/6/9/12,这些非整数是算出来的,不是选出来的。 ②引擎已经给出的东西确实被大面积绕过(圆角直接引用 0 处)。 ③最根本的是没有强制机制:396 个组件文件里只有 35 个用角色类,192 个直接写 <button> —— "怎么写都行"。

因此顺序是"补尺度 → 迁用量 → 加门禁",而不是先加门禁。 先加门禁会把 2,244 处一次报出来,反而挡住开发 —— 上游这次正是踩了这个坑(它的两条规则至今仍是 warn,因为自己的 codemod 没做完)。

§9

修复路线与目标态

所有条目都是微优化:不动布局结构、不动交互模型、不引入新依赖。P0 只改变量与少数内距,风险接近零。

P0 · 正确性与可见缺陷(1–2 天,不动设计取向)

  • ① 焦点可见性(§6.1):全局 *:focus-visible 从 outline: none 改成默认环 + 2px 偏移;craft-* 作为例外。无障碍收益最大的一条。
  • ② 修 z-[N] 22 处并补齐规则对任意值形式的覆盖(§7.3)。
  • ③ 边框中性化(亮 #E6E6E8、暗去蓝)+ 修 shadow-* 自引用(§1.2 / §2.5)。
  • ④ 暗色主按钮标签改墨色:3.89 → 4.52,品牌色不动(§6.2)。
  • ⑤ 让 RADIUS_EDGE/INNER 生效(或把主题字段拆成 edge/inner)(§2.1)。
  • ⑥ 画布锁色:default.json 写 navigator: #E9E9EA,标题栏与侧栏同源(§1.1 方案 A)。

P1 · 尺寸与一致性(3–5 天,改数值 + 少量组件)

  • ⑦ 命名行高:--row-sidebar 32 / --row-menu 30 / --row-list 36,侧栏与菜单改用 min-height;density 改为调行高。→ 解决"侧栏偏大"(§4)。
  • ⑧ 侧栏横向内距对称化(滚动条 gutter 补偿),并把首行与面板头对齐(§3.1 / §4)。
  • ⑨ 统一列宽与内容边:840 → 768;输入区与转录列同 padding(§3.2)。
  • ⑩ 状态统一:三档填充 + 选中态统一 + 气泡改用填充 token(§5)。
  • ⑪ 分隔线两档化 + 面板接缝与面板边框同权重(§1.2 / §3.3)。
  • ⑫ 卡片一档真实高程 + 输入框/代码块用下沉色(§1.3 / §1.4)。
  • ⑬ 紧凑断点的触摸目标放大(图标按钮 → 36px)(§6.3)。

P2 · 尺度与门禁(1–2 周,防止数字回到今天)

  • ⑭ 补四类 token:4 级字号、4 级圆角、3 档填充、命名行高 + 栅格(§2)。
  • ⑮ codemod 收敛:328 圆角 + 590 字号 + 204 填充 + 407 间距按映射表替换;--fill-*、--surface-* 真正落地。
  • ⑯ 提高角色层覆盖率:192 个手写 <button> 逐步迁到 craft-* —— 约束的落点(§7.4)。
  • ⑰ 加三条规则(禁止圆角/字号/填充字面量),先 warn 后 error;并把"hover 才出现必须带 data-touch-reveal"也做成规则(§5)。
  • ⑱ 单一来源:两份 index.css 合并为一份 tokens + 引用(§8.1)。
  • ⑲ 动效唯一来源 + 减少动效产品开关(§2.6 / §6.4)。

§10

方法、口径与不确定项

统计与测量口径

  • 像素测量:Pillow 逐像素扫描 —— 颜色取样、水平/垂直边界扫描、圆角弧线最小二乘拟合(残差 < 0.35px 才采信);标定 @2x(§0)。
  • 代码统计:范围 apps/electron/src/renderer、packages/ui/src、apps/webui/src、apps/viewer/src, 文件类型 .ts/.tsx/.css,正则命中次数 —— 不是 ESLint 运行结果,所以与 lint 报告可能有少量差异。
  • 对比度:WCAG 2.x 在 8 位 sRGB 上计算;我们的状态文字按 color-mix(in oklab, 色 50%, 前景) 推导。
  • 灰阶差:sRGB 通道值直接差,用于比较"画布/纸面"的相对亮度,不是对比度比。
  • 只读:两个仓库都没有文件被修改;本文档位于项目目录之外。

不确定项(不要当结论用)

  • 面板间隙里 4px 灰带的成分:推断是"缩放条 2px 线 + 两侧面板阴影叠加",未逐层验证;要改先确认是谁画的。
  • 回复卡圆角:代码在 TurnCard.tsx:2689 写 rounded-[8px],实测弧线却是 5–6 —— 可能截图里那张卡片是另一个带 overflow-hidden 的包装组件,落地前需确认是哪一层。
  • 列表头 58.5 css:只量到"顶边到下沿分隔线",组成(标题行 + 分组标签 + 间距)未逐层核对。
  • z-[N] 未被规则拦截的确切原因:确认了规则以 error 接入且这 22 处存在,但未逐行读规则实现定位是"任意值未覆盖"还是"文件被 exclude"。补规则前需确认。
  • 35 处非白名单阴影:包含配置里显式 off 的路径,未区分"豁免"与"真漏"。
  • 角色层覆盖率 35/396:是"含 craft-* 字符串的文件数",不是组件个数;真实覆盖率可能更低。
  • 行高 42 → 32 的观感:由上游 28 与我们的实测反推,未做渲染验证;建议 32 与 34 各试一版再定。
  • 方案 B 的"−43%":是灰阶差比值(23→13),不是感知亮度比;真实观感受边框/阴影影响,必须与 P0 的边界改动一起评估。
  • 暗色模式未实测:本文档的暗色是用我们的 token 值还原的,不是你截图里的暗色界面。

这份文档是什么。对 Phaneris 当前前端的一次系统性视觉审计:先用一张 Retina 截图(@2x)做逐像素实测建立基线, 再用正则统计覆盖 396 个组件文件(renderer 306 + ui 90),最后把两侧证据合并为八个维度与一份修复路线。 它由两份更早的分析合并而成 ——《逐像素微优化清单》(基于截图的实测)与《四问回复与全项目审计》(侧栏尺寸、token 归属、着色风险、硬编码统计) —— 重排为一条主线:基线 → 面 → 尺度 → 栅格 → 侧栏 → 状态 → 无障碍 → 体系与门禁 → 债务趋势 → 路线与目标态。

证据口径与边界。像素测量用 Pillow 逐像素扫描(颜色取样、边界扫描、圆角弧线最小二乘拟合,残差 < 0.35px 才采信); 代码统计是正则命中次数而不是 ESLint 运行结果;对比度按 WCAG 2.x 在 8 位 sRGB 上计算。不确定项集中列在 §10,请勿把推断当结论。 审计时点:2026-10-11(审计开始时工作区已有 361 项未提交改动,因此统计包含未完成工作)。
