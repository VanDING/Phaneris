# 治理阶段评估与下一阶段开发方向

状态：M0 于 2026-10-29 完成本机 Windows 候选收尾，见[实施记录](m0-closeout-implementation-2026-10-28.md)；M1–M3 仍为 proposed。
日期：2026-10-28，Asia/Shanghai。  
审查基线：本地 `main`，`3cfe8a6bd1516f3fd26c6bdbf94ac186c6670805`；包版本 0.5.4，其后另有工作目录与备份修复。  
范围：0.3.0（10 月 4 日）至 0.5.4（10 月 28 日），以及当前 HEAD 的两项修复。

本文依据本地 Git 历史、版本说明、实施与验收记录，以及关键生产路径的源码核对。没有运行付费模型任务、复测全产品、操作个人工作区数据或核查远端发布状态。历史结果按原版本与环境引用，不作为当前 HEAD 的全部验收结论。正式实施状态继续以[价值裁定台账](implementation-value-register-2026-10-13.md)为入口；本提案不自动重开其中已关闭的项目。

## 1. 结论

**这段时间以治理为主是合理的，且已经形成值得保留的产品基础；继续把全面治理作为下一阶段主线，边际收益已经不足。建议经过一次有明确终点的稳定性收尾，把主线切换到研究与文档成果的实际交付。**

三个判断需要分别成立：

1. **方向正确。** 文件与会话归属、权限、持久执行、压缩所有权、结果保全和可恢复性，决定用户能否把真实工作交给产品。这些工作不是纯粹的代码洁癖。
2. **执行曾有过度。** 某些保护扩大了阻断范围，治理数据进入生产热路径，验证与文档形成重复表示。10 月 26 日的连续性修复、10 月 28 日的精简已经在纠偏。
3. **收益证明尚不完整。** 已有较强的机械契约和故障恢复证据，但缺少同等强度的真实模型任务质量、成品可用性与日常使用效率对照。继续增加检查数量无法补上这类证据。

更准确的阶段描述是：**横向功能扩张放缓，已有能力的纵向可用性投入很大。** 并非完全停止新功能：Markdown 编辑、甘特改期、项目记忆、MCP 资源工具、Chat Starters、Run 新工作区都在这一时期交付。真正不足的是一个围绕用户成果组织、连续完成的主场景。

规划假设：优先服务当前研究、写作、文档与长期项目工作，以本机 Windows 为主要实用验证环境；尚未把大规模对外发行作为本轮前置目标。如果商业化或跨平台首发成为首要目标，发行工作的排序需要另行调整。

## 3. 应保留的治理方向

### 3.1 执行、事实与产品状态各自有明确职责

一个 Pi 主循环、宿主持有权限与效果边界、Session 持有对话自有文件，是适合当前规模的基础。它减少同一行为在不同入口出现不同语义的机会，也让后续产品功能复用既有能力。

尤其应保留：派发副作用前保存意图；未知结果不盲目重放；已经观察到的真实结果不会因记账失败而丢失；单个历史未知调用不会锁死整个会话。后两点来自真实故障推动的职责修正，说明治理已经开始用日常可用性校准自己。[连续性实施记录](durable-runtime-continuity-implementation-2026-10-26.md)

### 3.2 按真实数据归属治理，优先于按目录大小拆分

Session Foundation 把分支、导入导出、草稿、Artifact 工作副本、元数据写入与恢复放在同一归属模型下。这比为了减少一个大文件的行数而不断抽取模块，更接近用户收益：成果搬得走、改动留得住、重启后找得到。[Session 实施记录](session-foundation-implementation.md)

### 3.3 失败场景先行，保留可复现产物

隔离工作区、真实子进程、SQLite、浏览器与打包客户端流程，能够发现普通函数测试无法暴露的生命周期问题。PASS、FAIL、NOT RUN 分开记录也应继续保留。应调整的是测试选择和解释方式，不是放弃已有保护。[治理实施与验证](../verification/project-governance-implementation-2026-10-16.md)

### 3.4 简化已有机制，而非再增加一个管理层

10 月 28 日已移除派生 parity 写入、结算时重复 usage 审计、单元素 backend 分发、重复 policy 和死路径，并保留历史数据、兼容及有效验证。这个方向正确：减少生产路径上的无消费工作，同时不把“少代码”误当“可以删保护”。[复杂度实施记录](complexity-debt-implementation-2026-10-28.md)

## 4. 需要纠正的偏向

| 偏向 | 已观察到的证据 | 后续原则 |
| --- | --- | --- |
| 保护范围超过实际风险范围 | 历史未知工具曾让整段会话无法继续，普通用户被要求人工 reconciliation；后来取消此前台阻断 | 保护落在有风险的动作上；诊断与记账失败不得无差别阻断独立工作 |
| 契约正确被外推为任务效果更好 | Harness 的 132 场景、连续性整合后的 173 场景来自受控流程；记录明确没有真实模型质量对照 | 分别报告工程正确性、任务质量、成品可用性和用户接受 |
| 检查本身形成额外成本 | 重复 policy 已退役；当前 critical 仍有跨版本验收口径问题 | 一份执行定义；新增检查必须说明防止哪种独立失效，优先复用现有流程 |
| 中间验收通过，最终组合状态不够清楚 | 两份近期记录均在 theme-foundation 的 103 场景与 115 下限差异处中断；另有 usage/source activation/interruption 未闭环 | 针对同一候选源码与构建关闭实际失败，不能把不同版本的绿色结果相加 |
| 文档形式完整，当前状态仍漂移 | README 徽章仍为 0.4.0，正文另留 Pi 1.1.0；Harness 记录仍写未合并，而 Git 已进入 0.5.0 | 当前入口同步结论，历史记录保留当时状态；不再靠新增平行台账解决 |
| 对运行可解释性的投入，领先于成果可用性 | Run 已能呈现丰富事实；Office 预览仍主要使用文本转换，结构校验不包含版式质量 | 下一轮优先改善用户交付物，再依据具体诊断需求扩展 Run |

其中，组合验收问题是**所查实施记录中的未闭环事实**；本次没有重跑，不能直接判定它们全部仍是 HEAD 的生产缺陷。例如 interruption 断言可能仍要求旧的整会话阻断行为，必须先核对已经批准的现行契约；不能为了旧测试通过而恢复已退役行为，也不能无依据放宽断言。

关于质量边界，当前 [Artifact 校验](../../packages/shared/src/artifacts/storage.ts)验证编码、文件签名及部分 OOXML 必要内容；[Office 预览](../../packages/server-core/src/services/artifact-preview.ts)使用 MarkItDown 转换。这些都是有效能力，但无法证明文档分页、文字溢出、图表布局或公式结果正确。“可读取”“结构有效”“业务内容合格”“用户接受”是不同事实。

## 5. 开发方向的优先级

建议以“本地优先，围绕成果持续工作的 Agent 工作空间”作为下一阶段选择功能的依据。现有持久性与审计继续支撑它；用户首先感受到的是工作完成和接续，而不是系统内部机制增加。

| 候选方向 | 与当前需要的匹配 | 复用基础 | 建议 |
| --- | --- | --- | --- |
| 启动、续聊、文件归属和候选构建的关键收尾 | 直接影响每天能否使用 | 现有修复及 E2E | P0，有终点的收尾 |
| 研究报告与文档的成果内反馈、修改和交付 | 最贴近研究、写作与文档工作；收益可以直接检查 | Artifact revision/lease、Markdown 编辑、文件预览、来源材料、已有会话 | P1，下一主版本唯一主要功能线 |
| 项目跨日接续 | 长任务不应反复交代已确认要求和最新文件 | Project、SessionTaskContext、MEMORY.md、handoff、Artifact | P2，成果闭环可用后推进 |
| 将成熟重复工作保存为自动化 | 有潜力，但必须先证明一次任务可稳定交付 | Automation、预算、Source、Skill、运行记录 | 条件 P3，先选一个已被反复使用的场景 |
| Run 新图表、通用 replay/血缘图、更多自动决策 | 已有丰富诊断，尚缺增量任务收益证据 | Run 与 usage ledger | 暂不立项，按具体问题补最小能力 |
| 多代理平台、全量记忆、插件市场、前端重写 | 引入新的生命周期、权限或生态维护面 | 当前无必须扩建的证据 | 维持既有关闭状态 |
| 对外发行与多平台覆盖 | 取决于分发目标 | 当前发行门槛与构建链 | 单独决策，不绑架个人主场景开发 |

这个排序是基于现有能力和用户工作类型的产品判断，没有市场验证或用户规模数据支撑，不宣称已找到商业产品定位。

## 6. 顺序路线与退出条件

版本名是建议的里程碑标签，不是发布日期或已批准的版本承诺。按退出条件推进，默认单任务实施。

### M0：0.5.x 收尾——建立可日用的候选基线

**用户结果：启动后能工作，中断后能继续，成果保存在正确位置。**

仅处理以下范围：

1. 将当前已完成的工作目录、备份、启动与续聊修复装入同一候选构建，验证普通会话、项目会话、重启后会话的路径与成果一致。已写的修复不重复开发。
2. 收口 theme-foundation 下限、usage ledger、source activation、interruption 的已记录失败：逐项判断生产回归、批准后的契约变化、平台条件或 fixture 过期；保留依据和替代覆盖，禁止以降低门槛掩盖缺口。
3. 处理已定位的启动阻塞：当前 `storeFor()` 仍同步运行完整性检查，初始化还同步执行维护；历史调查在一个约 2.15 GB 数据库上测得单次完整性检查约 29 秒。这是单一样本，不能外推全部用户，但足以支持有界优化。先分离窗口可用、工作区可读与维护阶段，并验证故障库不会被当作健康库执行有副作用动作；具体线程/进程安排由测量决定。
4. 对齐当前入口的版本、合并状态和验收边界，保留历史记录的原始结论。没有必要为此新建文档治理系统。

源码依据：[Coordinator](../../packages/server-core/src/durable-runtime/coordinator.ts)、[Runtime 初始化](../../packages/server-core/src/durable-runtime/api/runtime.ts)；测量依据：[启动调查](../verification/startup-and-session-stability-investigation-2026-10-28.md)。

**退出条件：**支持范围内的关键流程与既有必需门禁有同一候选版本的有效结论；人工打断、重启、分支和成果接受均可复现；启动耗时按同机、同数据、冷暖状态分别比较，保留原有适用预算。数据丢失、误写目录、未知动作重复执行属于阻断；未纳入支持范围的平台与无关历史扩展单列。

M0 不要求先把全部历史警告、所有大文件、所有文档和全部平台问题清零。Windows 上不支持的 server 分发构建应在其支持的 Linux/macOS 环境验证，或明确不属于此次本地桌面候选范围，不能伪造全平台通过。已存在的发布门槛继续按实际发行目标生效。

### M1：建议 0.6——围绕一个报告反复修改，直到可交付

**核心体验：用户在报告中选中一段，直接提出修改；Agent 修改同一个成果，用户看到本次变化，并拿到检查过的最终版本。**

当前 [ArtifactWorkbench](../../apps/electron/src/renderer/components/content-panels/ArtifactWorkbench.tsx)已具备编辑、提交、接受、重修、校验和预览。此阶段新增的是把“对具体内容的反馈”与“实际交付质量”接进这条已有链路，不重做版本存储。

| 顺序 | 新增体验 | 最小实现范围 | 验收重点 |
| --- | --- | --- | --- |
| M1a | 从当前成果提出定点修改 | 先支持 Markdown 文段；反馈携带 Artifact、revision 和选中文本/位置，送回所属会话；没有选择时允许对全文反馈 | 不改错文件、不引用过期版本；中文、表格附近选区、用户同时编辑、跨重启均有覆盖 |
| M1b | 清楚看到这次改了什么 | 复用原 revision，提供文本变化及可定位的新版本；来源引用沿用可用文件/URL/位置，不建立全局血缘图 | 反馈作用于正确版本；外部修改产生可理解冲突；未要求修改的关键约束保持 |
| M1c | 交付当前版本及相应检查结果 | 首片以研究报告的 Markdown 和可视 PDF 交付为准；检查内容、引用与实际渲染，结果绑定被检查版本 | 文件可独立打开；引用回到正确材料；无已发现溢出/截断；改后旧检查不冒充新检查 |

DOCX、XLSX、PPTX 继续保留现有生成和预览能力。新增高保真能力逐格式验证渲染可行性、部署成本与检查方法，先选择真实高频的一种再扩展。M1 不承诺通用 Office 在线编辑、商业 Office 引擎或全格式分页质量；不自动重启已经关闭的 Univer/Native Design Layer 方案。

**代表任务：**给几份含互相矛盾信息的资料，完成一份带出处的报告；中途改变结论重点；对其中一段提出修改；导出当前版本；重启后继续修改同一成果。只围绕这条主场景做完整功能切片。

**退出条件：**真实模型能在固定任务及材料上完成此闭环；文件、来源、反馈位置与版本均对应；报告的内容质量经人工复核；失败与重试全部记录。结果必须相对当前基线减少可观察的手工转接或返工，而不是只增加一个按钮。

### M2：建议 0.7——项目成为可继续工作的入口

**核心体验：隔天进入项目，可以看到当前目标、已确认决定、最新成果和下一项待办，直接续做。**

当前 [ProjectInfoPage](../../apps/electron/src/renderer/pages/ProjectInfoPage.tsx)主要组织 Sessions、Assets、Settings；已有 [task context](../../packages/shared/src/prompts/task-context.ts)与[项目记忆追加](../../packages/session-tools-core/src/handlers/project-memory.ts)。新增的是把这些能力变成可操作的接续入口。

- 先提供“继续最近工作”：明确进入哪个 Session、使用哪个成果版本、还有什么用户问题未处理。
- 将用户确认的要求/决定与模型提出的工作记录区分，均能回到来源；已有文件与消息继续保有权威性。
- 优先从现有 Session、Artifact、任务状态和项目文件派生；确需新字段时才增加最小可编辑信息，不另建第二套任务事实库。
- 跨会话复用材料由用户选择或现有项目绑定驱动，不默认全量注入历史，不自动把模型推断写成永久事实。

**退出条件：**退出应用、跨日、压缩和新会话接续之后，能取得正确当前文件与已经确认的约束；后来的纠正覆盖过时工作记录；减少重复说明和寻找文件的动作。若 M1 的真实使用没有暴露明显接续摩擦，M2 应缩小范围或延后，不能仅因技术基础存在就扩建。

### M3：后续候选——把已经做好的工作保存为重复任务

例如固定资料源的周报或项目进展报告。复用 Automation、Source、Skill、预算和成果链路，使每次运行产出独立可检查的成果，失败可定位，暂停可生效。

**进入条件：**同一种人工发起工作已重复发生，输入与验收相对稳定，用户确实需要持续执行。先做一种任务；用户可检查有效权限与运行范围。M3 不新建 DAG 平台、自动审批者或多代理控制台。

**退出条件：**重复运行、停止、重启及来源失败下，成果与通知符合既定策略，无重复业务副作用。运行成功不等于成果已被用户接受。

## 7. 怎样证明下一轮投入有效

工程契约继续使用现有 VerificationRun/critical 与功能 E2E。新增的真实任务对照作为当前功能的验收材料保存，不建立通用评测平台或排行榜。

| 观察 | 记录方法 | 防止误读 |
| --- | --- | --- |
| 可交付任务 | 预先写明任务、材料、预期成果和内容/格式标准，逐项记录通过与失败 | 模型说“完成”、文件存在、运行 terminal 都不能单独判定任务合格 |
| 用户接受 | 记录明确接受的成果版本 | 接受动作不能反过来证明每一项事实和引用均正确；未接受不直接判失败 |
| 人工介入 | 分开记业务反馈、重新解释要求、找文件、恢复操作、外部排版返工 | 用户正常修改需求不是系统失败；因系统丢失信息而重复说明才是摩擦 |
| 到首个可用成果的耗时 | 分开记录连接、准备、模型、工具、检查和用户等待 | 不用一个 TTFT 数字代表整个工作效率 |
| 长任务连续性 | 对照中断前后要求、未消费输入、成果版本和已执行动作 | “下一轮能启动”不等于“任务已经正确接续” |
| 成本与体积 | 记录实际可知费用、辅助请求、Token、单任务材料与数据库增量 | 未知费用单列；不把一次清理后的磁盘减少外推为长期增长已解决 |

比较时固定模型、连接设置、资料、有效指令及候选版本；记录网络/服务波动。真实模型有随机性，保留重复运行和全部失败，不挑最好的一次。小样本用于定位本功能的瓶颈与退化，不发布普遍完成率提升的结论。尚未建立基线，因此本文不给出成功率、速度或收入的预测百分比。

关于辅助决策，保留现行显式选择和 fallback。只有对某一个实际功能取得质量、延迟、费用的对照证据后才调整默认值；不因“多一次模型判断”就推定更智能，也不因默认关闭就断言应删除。

## 8. 治理如何随开发继续

1. **每个迭代只有一个主要用户成果。** 治理跟随该成果的实际阻碍进入；数据损坏、权限错误、安全问题和发布阻断可单独插入。
2. **每个治理事项写清停止条件。** 明确失败、受影响用户路径、最小改动和验证结果；达到条件即收口，不顺势升级为全域重构。
3. **基础体验和设计规则保持稳定。** 继续修复可读性、性能及交互故障；没有真实流程收益，不再全仓改主题、控件尺度或表面组织。
4. **升级服务于任务需要。** 安全修复、服务兼容和已确定能力缺口优先；无关依赖大升级不与主功能、设计重做、状态机重构捆绑。
5. **同一候选构建承担最终结论。** 独立工作流避免并发覆盖共同构建输出；保持现有 pre-push 和适用发行检查，不以减少检查数量作为效率目标。
6. **只维护一个批准队列。** 本文经选定后把最小工作包登记到价值裁定台账，其余仍是条件建议；历史审计与研究不自动生成新的开发义务。
