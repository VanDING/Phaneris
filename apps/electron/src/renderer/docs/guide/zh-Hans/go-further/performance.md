# 性能

代理工作的时间和费用由模型、上下文、缓存、工具输出与实际请求共同决定。不要把静态估算当作某次运行的账单。

## 主要影响因素

- 长会话通常需要处理更多上下文，压缩和缓存会改变实际发送与计费量。
- 项目说明、已启用能力和常驻指令也占用上下文，应保持与目标相关。
- 大段工具输出会增加阅读和后续处理成本；优先限定文件、行数、字段和时间范围。
- 模型与思考等级应匹配任务。不同服务的 Token、缓存与价格口径可能不同。

## 可调整的方式

将工作目录指向准确材料，用技能复用方法，选取所需来源；机械工作采用合适的模型和思考等级。标题、分类等辅助能力有独立调用，启用后也应检查其真实请求和费用。

Prompt 缓存可影响延迟和计费，但是否命中由 provider 和实际请求决定，不能只凭启用选项就承诺节省比例。

## 压缩与延续

接近上下文上限时，执行器可能压缩较早内容。压缩有损，后续推理使用的是压缩后的上下文；原始历史与 Runtime 事实仍各自保留。重要约束应写在适当的项目说明、技能或当前请求中，不依赖模型永远记住最早一轮。

目标已变化或上下文混杂时，可新建会话并提供清楚的交接材料。连续性有价值，但不必通过无限增长的单一聊天维持。

## 如何测量

Run 工作台展示可获得的请求用量、时序和决策记录。首个文本增量、生成阶段和完整响应延迟属于不同指标，不能直接互换。缺失指标显示为未知；未知费用不算零。

本地可靠性事实还显示终态、未决 T1、任务预算和重复信号，可导出后按同一事实范围重算。重复不证明没有进展，`completed` 不证明用户接受；比较优化前后时应保留同一场景与环境证据。
