# API 发现

在有权访问的网页应用中，网络请求可以帮助理解其接口。优先查官方文档和受支持的接入方式；内部网页接口没有稳定兼容承诺。

## 工作步骤

1. 在浏览器面板打开应用并完成必要登录。
2. 执行目标范围内的操作，先以读取流程为样本。
3. 查看对应请求的方法、URL、参数、请求体和响应结构。
4. 确认是否有可供外部客户端使用的认证，再准备[API 来源](phaneris://docs/sources/apis)。
5. 测试来源，核对结果、分页、筛选与界面数据是否一致。

接口返回成功不代表业务结果正确，应检查对象、范围和记录数量。导出请求证据时剔除秘密和无关个人资料。

## 认证与边界

明确提供给客户端的 API Key、Token 或 OAuth 是可维护的接入基础。仅复制网页 Cookie、CSRF 值或临时签名通常依赖登录会话，易过期，也可能超出服务允许的接入方式。

遇到会话绑定或签名保护时，不应把绕过保护作为“发现 API”的下一步。保留浏览器流程，或向服务方确认官方接口。CSRF/签名的出现本身也不能证明存在另一个无认证接口。

## 接口形状

- 列表第一页不能说明如何分页；在界面翻页，核对游标、页码和筛选参数。
- 服务器直接渲染 HTML 时，读取页面可能比构建 API 来源更合适。
- GraphQL 接口需要维护查询和变量，还应检查官方支持范围。
- 写接口必须明确说明外部效果。使用原有账户权限调用，不代表已获得重复、无人值守提交的授权。

只配置当前确实需要的端点，并保留可验证样本。内部接口变化时更新配置；不要把一次抓包当作永久契约。
